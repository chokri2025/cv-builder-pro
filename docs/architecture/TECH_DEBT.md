# Tech Debt & Risk Register

Each item: files, why it's a problem, severity, and the **smallest safe change** — not a rewrite.
Severity reflects current production impact, not theoretical badness.

---

## Maintainability

### M1. No CI at all — Critical
**Files**: repo-wide (no `.github/workflows`, no other CI config).
Lint, typecheck, and test only run if a human remembers to run them locally. Nothing blocks a
regression from reaching `main` or from being deployed by Vercel (which only runs its own build,
not lint/test).
**Smallest safe change**: add one GitHub Actions workflow that runs
`pnpm install --frozen-lockfile && pnpm typecheck && pnpm lint && pnpm test` on push/PR. No code
changes required, ~30 lines of YAML.

### M2. `FormPanel.tsx` is a 573-line god component — High
**Files**: `artifacts/cv-builder/src/components/FormPanel.tsx` (573 lines, the largest file in
the repo), driven by a 20-field prop interface from `src/pages/CVBuilderPage.tsx:74-97`.
Owns all 7 CV sections (personal/summary/experience/education/skills/languages/projects) plus
template picker and save/clear controls in one component. Hard to review, hard to test in
isolation (it currently has zero tests), and any change to one section risks touching unrelated
render logic.
**Smallest safe change**: extract each section into its own component
(`PersonalSection.tsx`, `ExperienceSection.tsx`, ...) taking only the props it needs, with
`FormPanel` reduced to composition + the template picker. Do this incrementally, one section at
a time, with no change to `useCV`'s public shape — pure extraction, not a state-management
rewrite.

### M3. Route shape declared independently in three places — High
**Files**: `artifacts/cv-builder/src/App.tsx:22-31` (JSX `<Routes>`),
`artifacts/cv-builder/scripts/seo-routes.mjs` (`getPrerenderRoutes`/`getSitemapEntries`),
`artifacts/cv-builder/scripts/prerender.tsx:239-249` (per-`kind` render dispatch).
`scripts/seo-routes.test.ts` only checks agreement between the sitemap list and the prerender
list — **nothing checks agreement against `App.tsx`**. Adding a route to `App.tsx` without
updating `seo-routes.mjs` silently produces a crawlable-but-unprerendered page (served as a
duplicate of the homepage to crawlers — an SEO regression that ships silently).
**Smallest safe change**: add one test that imports `App.tsx`'s route config (or a small shared
route-descriptor array that both `App.tsx` and `seo-routes.mjs` consume) and asserts every
page-type in one appears in the other. Full unification (single source of truth for all three)
is the `TARGET_ARCHITECTURE.md` goal; the test alone catches the drift today without touching
runtime code.

### M4. Generated API code committed to git, un-enforced sync with hand-authored spec — Medium
**Files**: `lib/api-zod/src/generated/*`, `lib/api-client-react/src/generated/*` (generated by
`orval` from `lib/api-spec/openapi.yaml`), not listed in `.gitignore`, regenerated only by
manually running `pnpm --filter api-spec run codegen`.
Currently low-impact (nothing consumes the generated client), but the drift risk grows the
moment a real endpoint is added and someone hand-edits `openapi.yaml` without regenerating.
**Smallest safe change**: add a CI step (once M1 lands) that runs the codegen command and fails
the build if `git diff` is non-empty — cheap, catches drift the moment it starts to matter.

### M5. Doc/code drift in `replit.md` — Low
**Files**: `replit.md` claims `"react-query (via api-client-react) - API hooks"` as a dependency
of `cv-builder`; the actual `package.json` has zero `@workspace/*` dependencies, and
`cv-builder/tsconfig.json` references `../../lib/api-client-react` as a TS project reference
with no corresponding import anywhere in `src/`.
**Smallest safe change**: either remove the stale tsconfig reference and the false claim in
`replit.md`, or (if a near-term feature will consume `api-client-react`) leave a one-line comment
in `replit.md` noting it's provisioned-but-unused. Either way, ~2-line edit.

### M6. Duplicate "supported locales" concept — Low
**Files**: `artifacts/cv-builder/src/i18n.ts` (`SupportedLang`) vs.
`artifacts/cv-builder/src/data/market-copy/index.ts:13` (`LangCode`) — two independently
maintained unions of the same six language codes.
**Smallest safe change**: have `market-copy/index.ts` import `SupportedLang` from `i18n.ts`
instead of redeclaring it. Type-only change, no runtime behavior change.

### M7. `document.dir`/`document.lang` set in two places — Low
**Files**: `App.tsx:15-18` and `src/hooks/useLanguage.ts:11-20`, both independently derive
`dir`/`lang` from `i18n.language` and write to `document.documentElement`.
**Smallest safe change**: delete the effect in `App.tsx` and rely solely on `useLanguage.ts`
(already used elsewhere) — or vice versa. One of the two is redundant; ~10 lines removed.

### M8. Unused/vestigial scaffolding — Low
**Files**: `artifacts/cv-builder/components.json` (shadcn config with no `src/components/ui/`
directory using it), `scripts/src/hello.ts` (`@workspace/scripts`'s only file, a placeholder).
**Smallest safe change**: delete both if confirmed unused (quick grep already confirms no
imports reference either) — zero risk, pure cleanup.

## Accidental complexity / premature abstraction

### P1. A full typed-API + DB pipeline exists with zero consumers — Medium
**Files**: `lib/api-spec`, `lib/api-zod`, `lib/api-client-react` (483 LOC, including a genuinely
well-built 368-line fetch wrapper), `lib/db` (empty schema scaffold).
This is not "bad code" — `custom-fetch.ts` in particular is careful, production-quality work —
but it currently adds build/typecheck surface (3 of the workspace's `tsc --build` project
references are these packages) and onboarding confusion (`replit.md` implies it's wired up; it
isn't) for zero shipped functionality. It is speculative infrastructure for a backend that does
not exist yet.
**Smallest safe change**: don't delete it (it's cheap to keep and clearly intended for a future
"cloud save"/account feature — see `TARGET_ARCHITECTURE.md`), but **make the decision explicit**:
add a short note at the top of `lib/api-spec/openapi.yaml` and `lib/db/src/schema/index.ts`
stating what feature will consume them and that they're intentionally unwired for now. This
converts "is this dead code?" (a recurring question for every new contributor) into a one-line
answer.

### P2. `artifacts/api-server` declares dependencies it never uses — Low
**Files**: `artifacts/api-server/package.json` declares `@workspace/db` and `cookie-parser`;
neither is imported anywhere in `src/`.
**Smallest safe change**: remove both from `package.json` until a route actually needs them —
or, if DB/auth wiring is imminent, leave a comment. Either way, don't carry silently-unused
dependencies through `pnpm install` indefinitely.

### P3. Hand-rolled ZIP writer and raw OOXML generation — Low (flagged, not necessarily wrong)
**Files**: `src/lib/zip.ts` (119 lines, from-scratch CRC32 + ZIP directory headers),
`src/lib/docx.ts` (248 lines, hand-built OOXML XML).
This avoids a heavy dependency (`docx`/`jszip`) for a genuinely small, well-tested surface
(`docx.test.ts` covers both), and keeps the exported bundle small — a defensible trade-off, not
obviously wrong. Flagged here only so it's a **known, deliberate** trade-off rather than
something a future contributor "fixes" by pulling in a 200KB dependency without realizing why it
was avoided.
**Smallest safe change**: none required. Add a one-line comment at the top of `zip.ts`
explaining why it's hand-rolled (mirrors the existing, good comment already at the top of
`print-pdf.ts` for the same kind of decision).

## Performance

### PF1. All 6 locale bundles shipped upfront — Medium
**Files**: `artifacts/cv-builder/src/i18n.ts:5-10` statically imports all 6
`locales/*/translation.json` files (1604 lines total) into the initial JS bundle, regardless of
which language the visitor needs.
**Smallest safe change**: switch to i18next's lazy-loading backend (dynamic `import()` per
locale, keyed off the route's `:lang` param) — a localized, well-supported change to `i18n.ts`
only; no component code changes needed since `react-i18next`'s `useTranslation()` API is
unaffected.

### PF2. Unvalidated `:lang` route segment creates unbounded low-quality URL space — Medium
**Files**: `App.tsx:23-30` (`/:lang` accepts any string), filtered only after the fact in
`CVBuilderPage.tsx:48`.
Any arbitrary path segment (`/xyz123`) renders the homepage in English with a 200 status and a
distinct URL — a soft-404 / duplicate-content pattern crawlers penalize. (This is really an SEO
risk realized through routing; listed here and cross-referenced in the SEO section below.)
**Smallest safe change**: add a router-level guard — if `:lang` isn't in `SUPPORTED_LANGUAGES`,
render the existing `<Navigate to="/" replace>` catch-all instead of `CVBuilderPage`. A few-line
change to `App.tsx`'s route element.

## SEO architecture risks

### S1. Route drift risk — see M3 above (Critical/High, already covered).

### S2. Soft-404 on invalid `:lang` — see PF2 above (Medium, already covered).

### S3. Build-time prerender scale — Low today, worth monitoring
**Files**: `scripts/prerender.tsx` generates ~335 slugs × 6 locales + fixed pages ≈ 2000+ static
HTML files per build.
Not a current problem (build succeeds today), but this scales linearly with the SEO content
strategy (more skills/cities/locales = proportionally longer builds). No test or budget currently
guards build time.
**Smallest safe change**: none needed now; note it as a metric to watch (e.g., log build
duration in CI once M1 lands) before the page count grows another 5-10x.

## Testing gaps

### T1. Largest, most stateful component is untested — High
**Files**: `FormPanel.tsx` (573 lines) has zero tests. `CVBuilderPage.tsx`, `LandingPage.tsx`,
`SitemapPage.tsx`, `EuropassPage.tsx`, `CVPreview.tsx`, `AtsChecker.tsx` (component level, though
its underlying `ats-match.ts` logic is well tested) also have zero tests.
**Smallest safe change**: this is naturally solved by M2's extraction — test each new section
component as it's split out, rather than writing one large test for the current monolith.

### T2. `prerender.tsx` itself is untested — Medium
**Files**: `scripts/prerender.tsx` (279 lines) has no test; only its input
(`seo-routes.mjs`, via `seo-routes.test.ts`) is tested.
**Smallest safe change**: a single smoke test that runs the prerender output-assembly functions
(`assembleHtml`, `stripGenericSeoTags`) against a fixture HTML string and asserts no duplicate
`<title>`/`<canonical>` tags remain — doesn't require a full build.

### T3. No locale-key-parity test — Medium
**Files**: `src/locales/{en,fr,es,ar,tr,pt}/translation.json` — no test verifies all 6 files
have the same key set, so a missing translation key silently falls back (i18next default
behavior) rather than failing a build.
**Smallest safe change**: one small test that loads all 6 JSON files and asserts identical
(flattened) key sets.

### T4. No CI to run any existing test — see M1 (Critical, already covered).

## Frontend/backend boundary

### B1. `api-server` is dead in production but looks alive in the repo — High
**Files**: `artifacts/api-server` (169 LOC, `/healthz`, `/sitemap.xml`, `/robots.txt`), not
referenced by `vercel.json`'s build.
A contributor reading `replit.md` or the `artifacts/` directory would reasonably assume
`api-server`'s sitemap/robots routes are live; they are not — production relies entirely on the
statically generated files from `cv-builder`'s own build step
(`scripts/generate-sitemap.mjs`). This is duplicate logic (two implementations of the same
sitemap/robots generation, one dead) and a trap for future debugging ("why isn't my api-server
change showing up in production?").
**Smallest safe change**: add a one-line comment at the top of `artifacts/api-server/src/app.ts`
stating it is Replit-only / not part of the Vercel production deployment, and a matching note
in `replit.md`. Zero behavior change; removes the trap. (Whether to formally retire api-server or
give it a real production role is a `MIGRATION_PLAN.md` decision, not a docs fix.)

## Security / privacy

### SEC1. Wide-open CORS on `api-server` — Low today, High if ever exposed with real endpoints
**Files**: `artifacts/api-server/src/app.ts:56` — `app.use(cors())` with no origin restriction.
Currently low severity because the only endpoints are health/sitemap/robots (no sensitive data,
no mutation). Must not ship as-is if `api-server` ever gains real endpoints.
**Smallest safe change**: pass an explicit `origin` allowlist (the production domain(s)) to
`cors()` now, even though nothing sensitive depends on it yet — cheap insurance, one-line change.

### SEC2. Unsanitized header reflection into sitemap/robots output — Low
**Files**: `artifacts/api-server/src/app.ts:60-69,90-101` — reads `x-forwarded-host` /
`x-forwarded-proto` / `host` headers directly into the response body without validation against
an allowlist.
**Smallest safe change**: validate the host header against a small allowlist (production domain
+ localhost for dev) before using it to build URLs; fall back to a hardcoded default otherwise.

### SEC3. No runtime shape validation of `localStorage`-read `CVData` — Low
**Files**: `useCV.ts` already catches malformed JSON and falls back to `DEFAULT_CV_DATA`, but
after a successful `JSON.parse` it trusts the resulting object's shape. Structurally invalid
but valid JSON (for example `{"personal": null}`) can therefore reach render code and fail later.
**Smallest safe change**: validate the parsed value at the storage boundary before accepting it,
falling back to `DEFAULT_CV_DATA` when required fields/types are missing. A small hand-written
type guard is sufficient; use zod only if a shared runtime schema is useful elsewhere.

## What NOT to change

See `TARGET_ARCHITECTURE.md` §"Explicitly preserve" for the full list and rationale. In short:
the client-side-only privacy model, the print-based (not image-based) PDF export, the
shared-route-enumeration pattern (extend it, don't replace it), the offline ATS matcher, and the
`artifacts`/`lib` workspace boundary itself are all deliberate, currently-working decisions that
should survive every change proposed above.
